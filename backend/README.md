# API ZelaDF

**Publicada em 01/10/2026:** https://zeladf-api.vercel.app, deployment `dpl_HTj5YWQUJ4DTVwHgN8vmotiCcb7b`, projeto Vercel separado. Preview protegido em staging: `dpl_DHfWNac8eYZwxhkeFfpr32eHv9jF`. O cliente continua com as flags FastAPI desligadas. A produção respondeu aos smoke tests sem escrita, mas as rotas de backend que dependem de migrations ainda não foram habilitadas/validadas para contas reais. Detalhes e rollback em `../docs/BACKEND_PRODUCAO.md`.

Implementação local dos módulos 1 (fundação), 2 (leituras), 3 (solicitação de exclusão), 4 (avisos e fotos), 5 (confirmações), 6 (comunidade e status) e 7 (execução administrativa da exclusão). A raiz do projeto Vercel separado deve ser `backend/`; API de staging publicada e ensaiada; tráfego de produção ainda desativado. Evidências atuais em `../docs/BACKEND_PRODUCAO.md`.

O módulo 8 mantém o envio push na função TypeScript `api/send-push.ts` do projeto web até haver paridade demonstrada e decisão do produto. Não há rota push nem chave de `service_role` nesta API FastAPI. Cliente, webhook e servidor continuam desativados por padrão; consulte `../docs/BACKEND_PRODUCAO.md`.

Configuração do servidor: `SUPABASE_URL` é a URL HTTPS exata do projeto, `SUPABASE_PUBLIC_KEY` é a chave pública/anon, e `API_CORS_ORIGINS` contém origens exatas separadas por vírgula. Nenhum segredo administrativo é usado nestas rotas. O servidor confirma todo Bearer em `/auth/v1/user` e confere `iss`, `aud`, `role`, `exp`, `sub` e o ID retornado pelo Auth. Isso aceita tanto projetos HS256 quanto assimétricos, com uma consulta ao Auth por requisição autenticada.

Para a observação do módulo 9, configurar `API_KNOWN_CLIENT_BUILDS` como lista exata e curta, por exemplo `web/1.0.0,android/1.0.0`, apenas depois de relacionar cada rótulo a um build testado. A API aceita `X-ZelaDF-Client` no CORS e registra somente valores dessa lista; valores desconhecidos viram `unknown`. O rótulo identifica o build do código web, não a conta, instalação nem o `versionCode` Android. Logs com método e rota normalizada são agregáveis, mas não demonstram sozinhos ausência de tráfego direto no Supabase. Critérios de produção em `../docs/BACKEND_PRODUCAO.md`.

Instalação local em `backend/`: `python -m venv .venv`, `python -m pip install -r requirements-dev.txt` e `python -m pytest`. Para desenvolvimento, `python -m uvicorn server:app --reload`. `GET /health` confirma processo; `GET /ready` consulta a saúde do Auth sem expor detalhes.

O logger `zeladf.api` habilita explicitamente INFO e saída de console sem habilitar logs HTTP de terceiros. Todas as respostas sob `/api/v1/` têm `Cache-Control: no-store`, pois leituras também dependem da sessão. O deploy web exclui `backend/`; o `.vercelignore` desta pasta exclui ambiente virtual, caches, testes e o executor administrativo da publicação separada da API.

Rotas versionadas: `GET /api/v1/reports`, `GET /api/v1/reports/{id}`, `GET /api/v1/me/reports`, `GET /api/v1/me/votes`. A listagem exige `south`, `west`, `north`, `east`; aceita `category` repetida, `status` e `limit` (1 a 500, padrão 200). Resposta `{reports, truncated, source:"supabase"}`; a API busca `limit+1`. Os votos aceitam `report_ids` repetido, até 250 por chamada; o cliente divide a lista em lotes de 200 para ficar abaixo do limite de URL de 14 KB da Vercel. Todos os IDs são UUID. Erros têm `{error:{code,message,requestId}}`. Ausência de sessão em `/me/*` devolve 401; aviso inexistente ou invisível devolve 404.

Módulo 3: `GET /api/v1/me/deletion-requests/current` lê somente `id,created_at,status` pela RLS e devolve 404 se não houver pedido. `POST /api/v1/me/deletion-requests` exige corpo e query vazios, chama exclusivamente `request_account_deletion()` com o Bearer da conta e devolve `{id,createdAt,status}` após validar o protocolo. Repetições conservam o protocolo e a data pela unicidade/RPC do banco. Resposta inválida, falha do Auth ou do banco não confirmam recebimento. A API não executa a exclusão real.

**Rollback:** manter `VITE_API_READS_ENABLED=false` no build web/Android anterior. Para ensaio interno, definir `VITE_API_READS_ENABLED=true` e `VITE_API_URL` no build de teste. Em falha de leitura, a UI exibe erro; não retorna dados demo nem troca automaticamente para a Data API. Reverter a flag exige novo build web e, no Android instalado, novo APK. RLS, RPCs e acesso direto antigo devem continuar disponíveis durante essa fase.

O módulo 3 possui flag própria `VITE_API_DELETION_REQUESTS_ENABLED=false`. Para ensaio, definir `true` e `VITE_API_URL` no build de teste. Em falha de POST, o cliente consulta o protocolo atual pela API antes de apresentar erro; não repete pelo caminho antigo nem inventa confirmação. Para retornar ao fluxo Supabase atual, publicar build com a flag desligada. Não remover a RPC nem a fila ao reverter. O Android instalado exige novo APK para trocar a flag.

Módulo 4: `POST /api/v1/reports` exige Bearer, corpo com categoria, título, descrição, RA, endereço, latitude, longitude e `photoPath` opcional, mais `Idempotency-Key` UUID. Retorna `{report,initialVoteFailed}`. `PATCH /api/v1/reports/{id}` aceita somente categoria, título, descrição e `photoPath`; retorna `{report,photoCleanupFailed}`. `DELETE /api/v1/reports/{id}` retorna `{photoCleanupFailed}`. Erros usam o envelope comum e códigos 400/401/403/404/409/413/422/503. O limite JSON é 64 KiB; a foto de até 5 MiB é enviada pelo cliente diretamente ao Storage com JWT, em `<auth-user-id>/<uuid>.<jpg|png|webp>`. O backend consulta o Storage com o mesmo JWT, e as mutações usam RLS/RPC. A nova migration `20260924000100_fastapi_report_create_idempotency.sql` é requisito para criação: não ativar a flag sem comparar o schema remoto e testar/aplicar a migration em staging. Ela guarda chave e aviso na mesma transação e revalida termos e propriedade da foto. Falhas conhecidas de remoção entram em fila privada. `photo_cleanup.py` varre objetos gerenciados órfãos com mais de 24 horas; exige as migrations `20260926000100` a `20260926000400`, todas ensaiadas em staging. A reserva transacional protege contra reassociação enquanto a Storage API remove o arquivo; não existe cron de produção habilitado.

`VITE_API_REPORT_WRITES_ENABLED=false` mantém o CRUD direto atual. Em build de ensaio, definir `true` e `VITE_API_URL`; não há fallback automático em erro de escrita. A tela de criação reutiliza a chave e o caminho da foto enquanto os dados do formulário permanecem iguais. Após resposta perdida em edição/exclusão, atualizar os avisos antes de repetir. Rollback é um novo build com flag desligada, mantendo RLS, RPCs e Storage compatíveis com clientes antigos; Android requer novo APK.

Módulo 5: `PUT /api/v1/reports/{id}/vote` exige Bearer, UUID de aviso e JSON `{confirmed:boolean}` sem campos adicionais. Usa somente a RPC `set_report_vote` com o JWT validado da conta e devolve `{voted:boolean,confirmations:number}` da resposta canônica, sem IDs internos. Repetir o mesmo estado é idempotente pela RPC; 404 indica aviso ausente ou indisponível para confirmar. A API aceita corpo de até 64 KiB e responde com `Cache-Control: no-store`. `VITE_API_VOTES_ENABLED=false` mantém o voto direto atual, separadamente das flags de leitura e escrita de avisos. Falha ou resposta perdida não aciona fallback; a UI desfaz a alteração otimista e recarrega o estado. Rollback requer novo build web ou APK, mantendo a RPC disponível para clientes antigos. Antes de ativar, testar bloqueios/ocultação, duas contas, concorrência e contagem canônica com o banco real em staging.

Módulo 6: `PUT /api/v1/me/community-terms` aceita somente `{version:"2026-09-13"}`; `POST /api/v1/reports/{id}/flags` aceita `target`, `reason` e `details` até 500 caracteres e retorna `{id}`; `POST /api/v1/reports/{id}/author-block` e `DELETE /api/v1/me/author-blocks` não aceitam corpo. Estas rotas chamam apenas as RPCs comunitárias com JWT do usuário. `GET /api/v1/operator/access` devolve `{allowed}`; `GET /api/v1/operator/reports/{id}/status-history?page=N` exige papel de operador e devolve `{entries,hasMore}` em páginas de 100, sem ID Auth; `POST /api/v1/operator/reports/{id}/status` recebe `{newStatus,reason}` e chama exclusivamente `change_report_status`. O banco protege transição e histórico na mesma transação. Corpo JSON até 64 KiB, erros 400/401/403/404/413/422/429/503 e `Cache-Control: no-store` nas respostas sensíveis. A revisão de denúncias continua no canal administrativo privado de `release/COMMUNITY_MODERATION.md`; o papel de operador de avisos não recebe acesso à fila.

`VITE_API_COMMUNITY_STATUS_ENABLED=false` mantém os fluxos diretos atuais. Para ensaio, ativar somente em build de teste após confirmar as RPCs, RLS, origem CORS e a operação humana de moderação em staging. Falhas não disparam escrita direta; se a resposta da mudança de status se perde, o cliente confere a última entrada do histórico privado. Rollback exige novo build web ou APK e preserva RPCs/RLS para clientes antigos. Não há migration nova neste módulo.

Módulo 7: `account_deletion.py` é uma ferramenta administrativa local, sem rota HTTP e sem dependência do frontend. Exige `SUPABASE_URL` e `SUPABASE_SERVICE_ROLE_KEY` somente no ambiente do operador, `--request-id`, `--expected-user-id` e `--execute`. Pede no terminal o UUID aleatório de um registro restrito que documenta a verificação recente da identidade e da intenção do titular; envia apenas o SHA-256 dessa referência ao banco. A ferramenta não faz a verificação humana. O responsável deve confirmar o pedido e a conta no canal autenticado antes da execução; perda de acesso exige procedimento próprio. O papel `operator_users` não concede acesso a esta ferramenta ou às RPCs.

Depois da validação do ambiente e da migration `20260924000200_account_deletion_execution.sql` em staging isolado, executar dentro de `backend/`: `python account_deletion.py --request-id <uuid-do-pedido> --expected-user-id <uuid-auth-confirmado> --execute`. A RPC inicial compara os dois IDs com a fila, marca `in_review` e cria uma trava persistente; triggers e trava transacional recusam novas escritas da conta, inclusive com JWT antigo. A ferramenta remove pela Storage API lotes de até 100 fotos identificadas no metadado do bucket, repetindo até o inventário ficar vazio. Objetos de outros buckets, ownership conflitante e URLs legadas fora da pasta da conta exigem revisão manual e interrompem o fluxo. A RPC seguinte remove votos, avisos e tokens push numa transação; depois a ferramenta exclui o usuário Auth e verifica sua ausência. A RPC final confere Auth, Storage, banco e fila antes de deixar somente protocolo, hash da referência, resultado e timestamps. Falha em qualquer etapa mantém o estado para retomar com o mesmo comando; nunca trate `in_review` como exclusão concluída.

Não instalar a chave administrativa no projeto Vercel, no app ou em arquivos versionados. A exclusão Auth invalida refresh tokens, mas um access token emitido antes pode funcionar até expirar; o bloqueio no banco também rejeita escrita de uma identidade Auth já removida. O cliente aberto deve encerrar a sessão local quando detectar a invalidação; isso ainda precisa de ensaio em web/Android. Esta rotina não está ativa remotamente: exige reconciliação do schema, teste real de Storage/Auth/RLS com duas contas, backup/ensaio de restauração, responsável, canal e prazo definidos. Depois de começar um job, não remova a migration como rollback; retome ou investigue o job.

**Pendente para ativação:** concluir o portão do módulo 0, testar duas contas reais e bloqueios/avisos ocultos em staging, observar origem CORS Android, medir p95, ensaiar deploy preview Vercel e navegador/Android. Para o módulo 3, confirmar sessão expirada, isolamento entre contas, repetição de pedido, falha do banco e operação humana de privacidade. Nenhuma migration ou deploy é parte desta implementação local.

## Validação e operação atuais

A URL https://zeladf-api-staging.vercel.app usa Supabase staging e somente chave pública. O pacote usa `vercel.json` com framework FastAPI e Python 3.12. Execução real, incluindo remoção Auth/Storage e limpeza de órfãos: 66 verificações aprovadas; 18 testes Python locais. Os trechos anteriores de requisitos de ativação continuam aplicáveis à produção.

Para ensaio explícito, configurar `STAGING_PROJECT_REF` no processo e executar `python tests/live_staging.py`; `STAGING_API_URL` opcional seleciona a URL de staging autorizada no script. Ele obtém credenciais da CLI em memória, cria contas sintéticas e remove seus fixtures ao final. Nunca usar produção.

Limpeza administrativa: `python photo_cleanup.py --execute --max-batches 10`, com `SUPABASE_URL` e `SUPABASE_SERVICE_ROLE_KEY` somente no ambiente protegido do operador. O worker não é publicado na Vercel nem aceita disparo pelo cliente. Não agendar em produção antes de backup, promoção do banco e definição de operação. Ver `../docs/BACKEND_PRODUCAO.md`.
